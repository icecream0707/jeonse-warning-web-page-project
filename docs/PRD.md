# 전세 위험 진단 PRD

용어는 [CONTEXT.md](../CONTEXT.md)를 따른다.

## 목적
1. AI 코딩 도구(Claude Code + 스킬)로 요구사항 → 설계 → 구현 → 테스트 → 배포를 처음부터 끝까지 경험한다.
2. 실제 공공데이터를 수집·가공한 포트폴리오 결과물을 만든다.

개인 연습용이며 상용 서비스가 아니다.

## 문제
전세 계약 전에 확인할 정보(시세, 건물 정보, 권리관계)가 여러 곳에 흩어져 있고 용어가 어렵다. 세입자는 중개사 말에 의존해 계약하기 쉽다.

## 범위 (MVP)
- 대상: 서울 아파트, 단지 단위.
- 입력: 도로명주소 검색 API로 고른 주소 + 전용면적(그 단지의 거래 면적 목록에서 선택) + 보증금. 동은 선택.
- 출력: 위험 신호 나열 + 체크리스트. 종합 등급 없음.
- 안전 판정이 아니며, 근저당·호 차이는 반영되지 않는다고 화면에 명시한다.

## 위험 신호
### 1. 전세가율
- 보증금 ÷ 같은 단지·전용면적 ±1㎡의 최근 12개월 매매 실거래가 중앙값.
- 동 구분: 단지에 실제 동이 2개 이상 있으면 사용자가 동을 고른다("모름" 가능). 동이 없거나 하나뿐인 단지는 동 선택을 보여주지 않는다. 비교 순서는 선택한 동 12개월(3건 이상) → 단지 전체 12개월 → 단지 전체 24개월 → 거래 부족. 어느 단계로 계산했는지 화면에 표시한다. "모름"이면 동별 중앙값을 나란히 보여준다.
- 구간(설정 상수): 70% 미만 여유 있음(초록), 70~80% 빠듯함(노랑), 80% 이상 위험(빨강).
- 가로 막대에 70/80/90% 눈금 표시. 90%는 HUG 보증 한도 참고선.
- 최저·중앙값·최고와 거래 건수를 함께 보여준다.
- 거래 부족: 3건 미만이면 24개월로 한 번 확장(기간 표시). 그래도 3건 미만이면 계산하지 않고 "거래 부족"을 표시한다. 다른 단지로 대체하지 않는다.
- 구간 근거(HUG 공개 안내 조사 요약, 2026-10-12 기준, 1차 자료 직접 확인 전):
  - 80%: HUG 예방 안내의 참고선. (근저당 등 선순위채권 + 보증금) ≤ 주택가격 80%이면 일반적으로 안전한 계약으로 본다. 법령상 공통 기준은 아니고 안전 보장도 아니다.
  - 90%: HUG 보증 가입 심사선. (보증금 + 선순위채권 등) ≤ HUG 인정 주택가격 × 90%. 90%는 현행 기준이며 80% 하향 시행은 확인되지 않았다.
  - 70%: 우리 쪽 완충선. 우리는 선순위채권을 보지 못하므로 80% 도달 전에 "빠듯함"을 띄운다.
- 눈금 90%는 "HUG 보증 가입 심사선(선순위채권 포함 기준)"으로 표기한다.
- 한계: HUG는 KB·부동산테크 시세 등을 주택가격으로 쓰고, 우리는 실거래가 중앙값을 쓰므로 값이 다를 수 있다.

위반건축물은 위험 신호가 아니다. 건축물대장 API에서 위반 표시 필드를 확인하지 못해 체크리스트 7번으로 둔다. 건축 인허가 기록 유무로 위반을 추정하지 않는다(구축 건물 오탐, 허가받은 건물 안의 불법 증축 미탐).

## 체크리스트 항목 (초기)
1. 등기부등본에서 근저당·압류·가처분 확인. 근저당 + 보증금이 시세의 80% 이내인지 계산
2. 선순위 보증금(다른 세입자) 규모 확인 (HUG는 선순위채권이 주택가격 60% 초과 시 가입 제한)
3. 집주인 본인 확인과 계약 당사자 일치
4. 국세·지방세 체납 여부(납세증명서)
5. 인근 시세 직접 확인 (거래 부족 시 강조)
6. HUG 전세보증보험 가입 가능 여부 조회 (보증금 상한: 수도권 7억 원)
7. 건축물대장에서 위반건축물 표시 확인 (정부24 또는 세움터 열람)

## 데이터
- 매매 실거래가: 수동 배치 스크립트로 서울 아파트 최근 24개월분을 SQLite에 저장. 사용자 요청 시에는 공공 API를 호출하지 않는다.
- API(RTMSDataSvcAptTrade/getRTMSDataSvcAptTrade): 요청은 구 코드(LAWD_CD, 5자리) + 거래연월(DEAL_YMD, 6자리) 단위라 서울 25구 × 24개월 = 600회 안팎. numOfRows는 4000까지 되는 것을 확인(사용자). 한 번에 4000행을 받으면 대부분 구·월이 1회로 끝난다. 받은 건수가 totalCount보다 적으면 다음 쪽을 요청하고, 그래도 모자라면 적재를 실패로 처리한다. 일일 한도 1만 회(사용자 확인). 이후 갱신은 최근 월만.
- 응답 필드(샘플 확인): aptDong, aptNm, buildYear, dealAmount(쉼표 포함 문자열), dealYear/Month/Day, excluUseAr, floor, jibun(예 "202-3"), umdNm, sggCd, cdealType/cdealDay(해제), rgstDate(등기일).
- 정제 규칙:
  - dealAmount의 쉼표를 제거한다.
  - cdealType 또는 cdealDay가 비어 있지 않은 거래(해제)는 제외한다.
  - aptDong이 공백이면 동 미상, aptNm과 같은 값이면 동 없음(단일 동 추정)으로 본다. 추정이 맞는지는 적재 후 같은 단지에 다른 동 값이 섞이는지 검사한다.
- 주소 검색 API(business.juso.go.kr/addrlink/addrLinkApiJsonp.do, resultType=json, 서버에서 호출): 샘플 응답 확인. 쓰는 필드는 admCd(10자리), emdNm, lnbrMnnm(지번 본번), lnbrSlno(지번 부번), mtYn, bdKdcd(1=공동주택), bdNm, totalCount.
- 주소 매칭 키: 실거래가의 sggCd = admCd 앞 5자리, umdNm = emdNm, jibun = lnbrMnnm, 부번이 0이 아니면 "-부번" 붙임(예 "202-3"). 서울 실거래가는 이 셋이 같은 행을 단지로 본다.
- 매칭 검증(리센츠, 송파구 11710, 2024-09 샘플): 실거래가 sggCd=11710, umdNm=잠실동, jibun=22, aptNm=리센츠는 주소 결과(admCd 1171010100, emdNm 잠실동, lnbrMnnm 22, lnbrSlno 0)와 일치한다. 실거래가 aptDong은 "245"처럼 "동" 접미사가 없다. 화면에서는 "동"을 붙여 보여준다.
- 주소 검증: admCd가 11로 시작하지 않으면 "서울만 지원", bdKdcd가 1이 아니면 "공동주택이 아님", mtYn이 1이면 지원 안 함. 검색 결과 중 bdKdcd=1인 것만 남기고, 2개 이상이면 목록에서 고르게 한다(예: "잠실동, 리센츠"는 리센츠 본동, 리센츠 상가(bdKdcd=0, 지번 22-6), 리센츠빌 3건이 나온다. 도로명으로 검색하면 1건이다).
- 지번으로 못 맞추면 같은 sggCd·umdNm 안에서 bdNm과 aptNm을 정규화해 비교하고, 그래도 안 되면 후보 단지를 보여준다.
- 응답 문서 표의 lnbrSlno 설명은 "읍면동일련번호"로 잘못 적혀 있다. 실제 응답에서는 지번 부번이고 일련번호는 emdNo다.
- 건축물대장 조회는 MVP에서 쓰지 않는다. 위반건축물 자동 판별을 뺐기 때문이다.
- 주소 매칭 실패 시 "해당 아파트를 찾지 못함"으로 종료.

## 기술
Python 백엔드(FastAPI), SQLite, React(Vite, 얇게). 배포는 무료 호스팅에 코드와 DB 파일 업로드. Docker 제외.

배포: Render 무료 웹 서비스(GitHub 저장소 연결). FastAPI가 빌드된 React(`frontend/dist`)를 함께 서빙해 서비스 하나로 운영한다. 첫 접속이 느릴 수 있다(슬립). DB 파일(`backend/data/jeonse.db`, 약 18.5MB)은 저장소에 같이 올린다(커지면 Git LFS 검토). 저장소는 공개(public). 서버에는 `JUSO_KEY`만 환경변수로 넣고, 공공데이터 키는 서버에 올리지 않는다(적재는 로컬에서). 설정은 `render.yaml`, 실행·배포 방법은 `README.md`.

## 배운 점
1. **세부사항을 먼저 캐묻는 과정(grill)이 가장 중요했다.** 코드를 쓰기 전에 질문으로 걸러낸 것들이 나중에 비싼 수정이 될 뻔했다.
   - 전세가율은 같은 면적끼리 비교해야 하는데 처음 요구사항에는 전용면적 입력이 없었다. 입력 설계를 다시 짚다가 발견했다.
   - "실거래가에는 동·호가 없다"는 처음 가정이 틀렸다. 실제 응답을 보고서야 동 구분이 된다는 것을 알았고, 그 결과 동 선택과 동별 비교 기능이 생겼다.
   - "위반건축물을 인허가 기록 유무로 추정"하자는 아이디어는 구축 건물 오탐과 불법 증축 미탐 때문에 버렸다. 못 보는 것은 체크리스트로 내리는 것이 정직했다.
   - 안전/위험 같은 말 한마디(예: "이상 없음")도 사용자에게 가짜 안심을 줄 수 있어 이름을 정했다.
2. **API의 정보 양식을 직접 분석하고, 서로 다른 API를 이어 붙이는 부분의 예외를 처리하는 일이 가장 큰 위험이었다.** 문서나 요약만 믿지 말고 실제 응답 샘플을 받아서 확인해야 했다.
   - 주소 API 문서는 `lnbrSlno`를 "읍면동일련번호"라고 적었지만 실제로는 지번 부번이었다.
   - 실거래가의 `aptDong`은 "245"(접미사 없음), 빈 값, 단지명과 같은 값이 섞여 온다. 해제 거래는 별도 필드로만 구분된다.
   - 실거래가와 주소 API는 키가 서로 달라 `시군구코드 + 읍면동명 + 지번`으로 이어 붙였고, 지번이 안 맞는 경우를 위해 이름 비교 폴백을 만들었다.
   - 한 번에 받을 수 있는 행 수, 오류 응답이 두 가지 형식(`header`, `cmmMsgHeader`)으로 오는 점, 신고 지연, 개명으로 한 지번에 단지명이 둘인 경우 모두 실제 데이터를 보고 알았다.
   - 일부만 받고 조용히 넘어가거나(`totalCount` 불일치), 해제 거래가 남는 문제처럼 "조용한 실패"가 가장 위험했다.

## 구현 현황 (2026-10-12)
- 테스트 대상 모듈: parse_trade, parse_response, resolve_address, diagnose(전세가율, 동별 중앙값), list_options, store(replace_month 포함), match_complex(지번이 안 맞을 때 이름으로 찾기), dong_check, API 엔드포인트, 월 계산. 테스트 68개 통과(화면 서빙 포함).
- 수동 확인: 적재 배치(load_trades.py), React 화면. 리센츠(올림픽로 135)로 주소 → 면적 → 보증금 → 결과 흐름 확인.
- 코드 리뷰(ponytail-audit) 후 수정: 해제 거래 정리(구·월 통째 교체), 결과 카드 입력 불일치, 서울 외·산·거래 없는 후보 걸러내기, DB 경로 고정, 오류 메시지, 요구 패키지 버전 고정(httpx2).
- 운영 변수: `jeonse/config.py`의 `DATA_EXTRACTED_AT`는 load_trades.py를 다시 돌린 뒤 직접 고친다(화면에 추출일로 표시).
- 이름 폴백은 이름이 정규화(공백·기호·"아파트" 제거) 후 정확히 같을 때만 맞춘다. 부분 일치는 실패가 많을 때 추가.
- 동 규칙 점검: load_trades.py 끝에 "단지명을 동으로 적은 거래와 실제 동이 섞인 단지" 목록을 출력한다. 아직 전체 적재로 돌려 보지 않았다.
- 남은 일: 배포, 한계 문구 점검, 전체 재적재와 동 규칙 점검 결과 확인, 공공데이터 키 재발급.

## 테스트
전세가율 계산, 거래 부족 판정, 구간 판정은 단위 테스트. 공공 API는 저장한 샘플 응답으로 대체. 화면은 수동 확인.

## 한계
이 서비스는 안전 판정이 아니다. 아래는 구조적으로 못 보거나 틀릴 수 있는 부분이다.

**못 보는 위험**
- 등기부 권리관계(근저당, 압류, 가처분)와 선순위 보증금은 자동 판별하지 못한다. 그래서 전세가율은 HUG 기준보다 낙관적으로 나온다.
- 집주인의 세금 체납, 신용 상태, 계약 당사자의 진위는 보지 못한다.
- 위험 신호가 전세가율 하나뿐이다. 위반건축물도 자동 판별하지 못한다. "여유 있음"이어도 다른 위험이 있을 수 있다.

**가격 데이터**
- 실거래가 상세 API에는 동 구분이 있다(사용자 확인). 호는 구분하지 못한다. 동 값이 비어 있는 거래가 있을 수 있다.(미확인)
- 허위 신고나 담합 거래를 걸러내지 못한다. 중앙값과 거래 건수 표시로 영향을 줄일 뿐이다.
- 실거래가는 신고 지연이 있어 최신 시세를 반영하지 못한다. 수동 배치라 DB가 오래될 수 있다.
- HUG는 KB·부동산테크 시세 등을 쓰므로 우리 값과 다를 수 있다.
- 거래 부족인 단지는 전세가율을 계산하지 못한다.
- 동 기준 비교는 실제로 거의 켜지지 않는다. 적재 데이터(서울 25구, 2024-11~2026-10, 13만 4,410건, 단지 6,761개) 기준으로 리센츠(잠실동 22)는 85㎡ 195건, 28㎡ 130건, 124㎡ 34건, 60㎡ 18건이지만 동별로는 한 동에 24개월 동안 1~7건(201동 5건, 202동 7건, 203동 1건)이라 "동 12개월 3건 이상"을 못 채우고 대부분 단지 전체 기준으로 넘어간다. 동 선택의 가치는 "동 모름"일 때 동별 중앙값을 나란히 보여 주는 쪽에 있다.
- 동 구분이 되는 단지는 일부다: 실제 동이 2개 이상 2,506개, 1종뿐 1,300개, 동 칸이 전부 빈 단지 2,955개. 거래 행의 16.3%는 동이 비었거나 단지명과 같아 동 미상으로 처리된다.
- 같은 지번에 단지명이 둘 이상인 곳이 33개(개명 추정)라 단지 매칭은 이름이 아니라 지번으로 한다.

**기준값**
- 70/80% 구간은 HUG 공개 안내를 참고한 값이며 법적·공식 기준이 아니다.
- HUG 기준은 변경될 수 있다(2026-10-30 변경 예정). 조사 내용은 1차 자료 직접 확인 전이다.

**범위**
- 서울 아파트만 지원한다. 빌라, 오피스텔, 다가구, 서울 외 지역은 판별하지 못한다.
- 주소를 단지로 매칭하지 못하면 진단하지 않는다.
- 호 단위 판별은 하지 않는다.

**운영**
- 연습용 프로젝트이며 법률·금융 자문이 아니다. 실제 계약 판단에 쓰면 안 된다.
- 무료 호스팅에 SQLite 파일을 올리는 구조라 동시 사용자와 데이터 갱신을 고려하지 않았다.

## 제외
관리비 비교, 종합 등급, 호별 판별, 빌라·오피스텔, 서울 외 지역, 자동 수집 스케줄, Docker.

## 미확인
- 공공 API 요청 형식·호출 한도. 실거래가 상세 API의 동 필드는 사용자가 확인했으나 필드명, 빈 값 비율, 조회 가능 기간, 호 포함 여부는 미확인.
- 위반건축물 필드: 건축HUB 기본개요, GIS건물통합정보, 건축데이터 민간개방, 서울 열린데이터 광장 표제부에서 못 찾음. 항목표 확인 시 위험 신호로 되살릴 수 있음.
- HUG 기준 수치(90%, 60%, 상한 7억)는 조사 요약 기준이며 HUG 공식 페이지 직접 확인 전. 2026-10-30 제도 변경 공지가 있어 구현 전 재확인.
- 동 선택 규칙(전세가율 비교 단위)은 결정 대기 중.
